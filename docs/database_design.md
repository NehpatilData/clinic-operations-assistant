# Database Design

## 1. Overview

The Clinic Operations Assistant uses Microsoft SQL Server to persist
clinic administrative enquiries and their workflow information. The
configured database is `ClinicOperationsDB`, and the main table is
`dbo.clinic_requests`.

The Python application connects through `pyodbc` and the SQL Server ODBC
Driver 18. The current connection configuration targets a local SQL
Server Express instance, uses Windows trusted authentication, and sets
`TrustServerCertificate=yes` for local development.

## 2. Design goals

The database supports:

-   Retaining the original enquiry message.
-   Storing category, summary, preferred date/time, and
    missing-information details.
-   Tracking enquiry workflow status.
-   Recording safety and human-review flags.
-   Managing follow-up status and notes.
-   Saving draft replies for staff review without automatically sending
    them.

This is an administrative workflow tool, not a clinical diagnosis or
autonomous decision-making system.

## 3. Logical data model

The current application uses one main table:

``` text
dbo.clinic_requests
    ├── request_id (identity primary key)
    ├── original_message
    ├── category
    ├── preferred_date
    ├── preferred_time
    ├── summary
    ├── missing_fields_json
    ├── status
    ├── safety_flag
    ├── needs_human_review
    ├── draft_reply
    ├── created_at
    ├── sender_phone
    ├── follow_up_status
    ├── follow_up_notes
    └── reviewed_at
```

Each row represents one enquiry. The supplied code and screenshots do
not show separate patient, appointment, staff, or audit tables, or
foreign-key relationships to such tables. This document does not assume
those entities exist.

## 4. Table responsibilities

`dbo.clinic_requests` combines enquiry content with operational workflow
state.

-   **Identity:** `request_id` uniquely identifies the enquiry and is
    generated by SQL Server.
-   **Original content:** `original_message` preserves the submitted
    message.
-   **Analysis results:** `category`, `summary`, `preferred_date`,
    `preferred_time`, and `missing_fields_json` store classification and
    extracted information.
-   **Workflow:** `status` tracks the current processing state.
-   **Safety and review:** `safety_flag` records safety-screening
    outcomes; `needs_human_review` records the need for staff oversight.
-   **Draft response:** `draft_reply` stores an administrative draft for
    staff review.
-   **Creation timestamp:** `created_at` is non-nullable and defaults to
    `getdate()` in SQL Server.
-   **Follow-up:** `follow_up_status` and `follow_up_notes` track
    follow-up activity.
-   **Review timestamp:** `reviewed_at` is nullable and is set by
    application code when status changes to `in_progress` or
    `completed`.

## 5. Schema defaults

The SQL Server screenshots show these defaults:

  Column                 Default
  ---------------------- ----------------
  `status`               `new`
  `safety_flag`          `0`
  `needs_human_review`   `1`
  `created_at`           `getdate()`
  `follow_up_status`     `not_required`

`request_id` is an identity primary key. The primary-key index is shown
as clustered, unique, enabled, and primary.

## 6. Database access layer

The `src/database.py` module provides these operations:

  -------------------------------------------------------------------------------------
  Function                                          Responsibility
  ------------------------------------------------- -----------------------------------
  `get_connection()`                                Opens a connection to SQL Server.

  `save_enquiry(...)`                               Inserts an enquiry and returns its
                                                    generated `request_id`.

  `get_all_enquiries()`                             Retrieves enquiry and follow-up
                                                    fields, ordered by descending
                                                    request ID.

  `update_enquiry_status(request_id, new_status)`   Validates and updates workflow
                                                    status; sets `reviewed_at` for
                                                    `in_progress` or `completed`.

  `update_follow_up_details(...)`                   Validates and updates follow-up
                                                    status and notes.

  `update_draft_reply(request_id, draft_reply)`     Rejects empty drafts, saves the
                                                    draft, and sets
                                                    `needs_human_review` to true.

  `get_enquiry_draft_context(request_id)`           Retrieves message, category,
                                                    summary, missing fields, saved
                                                    draft, and safety flag.
  -------------------------------------------------------------------------------------

## 7. Transactions and query safety

Write operations commit after successful inserts or updates. On
exceptions, they roll back and re-raise the error. Connections are
closed in `finally` blocks.

SQL statements use parameter placeholders (`?`) for values instead of
concatenating user-provided values into SQL text.

## 8. Application workflows

### Enquiry creation

1.  Staff enters an enquiry in the Streamlit interface.
2.  A keyword-based safety screen runs before routine AI processing.
3.  Routine messages can be processed by the AI service and saved.
4.  If safety screening fails or potentially urgent language is
    detected, the application follows a human-review path and blocks
    routine draft generation for safety-flagged enquiries.
5.  The application saves the enquiry and displays the request
    identifier when the database operation succeeds.

### Status updates

Supported status values are `new`, `awaiting_information`,
`in_progress`, and `completed`. The update function validates the value
and checks that the record exists. For `in_progress` and `completed`, it
writes the current application-server timestamp to `reviewed_at`.

### Follow-up updates

Supported values are `not_required`, `pending`, `contacted`, and
`completed`. The function verifies that the enquiry exists, trims the
notes, updates the record, and commits the transaction.

### Draft replies

The application retrieves the enquiry context before draft management.
If `safety_flag` is true, routine draft generation is blocked and the UI
displays a human-review warning. Otherwise, the AI service may prepare
an administrative draft. Saving a draft sets `needs_human_review` to
true. The application does not automatically send the draft.

## 9. Safety and human oversight

-   Keyword screening may miss urgent language or flag benign text.
-   A safety flag is not a diagnosis or a clinically validated risk
    assessment.
-   Flagged messages must follow the clinic's established human-review
    and escalation procedures.
-   AI-generated classifications, summaries, and drafts require staff
    review.
-   The application should not make autonomous clinical decisions.

A production system would also need suitable access controls, audit
requirements, retention policies, monitoring, and documented escalation
procedures.

## 10. Configuration and deployment

Current local connection settings:

-   Server: `localhost\SQLEXPRESS`
-   Database: `ClinicOperationsDB`
-   Driver: `ODBC Driver 18 for SQL Server`
-   Authentication: Windows trusted connection
-   Certificate handling: `TrustServerCertificate=yes`

This configuration is intended for local development. A hosted
application cannot connect to the developer's `localhost` database.
Deployment requires a reachable, secured database and
environment-specific configuration.

Do not commit production credentials to source control. Use environment
variables or the hosting platform's secrets manager. Review TLS
certificate validation and database permissions before production use.

## 11. Limitations and future improvements

Potential improvements include:

-   Add database-level check constraints for allowed status values if
    appropriate.
-   Add indexes based on measured query patterns and performance needs.
-   Add an audit trail for staff changes if required by policy.
-   Define role-based access, retention, backup, and recovery
    procedures.
-   Add automated database tests using controlled mocks or a dedicated
    test database.
-   Consider separate patient, appointment, or audit tables if the
    domain grows and those entities become necessary.

These are recommendations, not claims that those constraints, indexes,
or related tables already exist.

## 12. Verification checklist

Before using this as a production specification:

-   Verify all column definitions directly in SQL Server after schema
    changes.
-   Confirm whether database-level check constraints exist for workflow
    values.
-   Confirm access controls, backup, and retention arrangements.
-   Test database failure and transaction rollback behavior.
-   Ensure no real patient data, API keys, or credentials are committed
    to the public repository.
